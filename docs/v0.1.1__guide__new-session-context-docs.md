**Purpose:** Define which documents to provide when starting a clean context session for an AI agent working on the Issues-FS ecosystem.

---

## Overview

When an AI agent begins a fresh session on the Issues-FS project, it starts with zero context about the codebase, architecture, conventions, and coordination model. The documents listed below provide the context needed to work effectively. They are organized into tiers so that sessions with limited token budgets can prioritize the most critical material.

**Total corpus assessed:** 9 primary documents, plus 22 additional documents across `to_classify/` and `development/`.

**Total lines across primary docs:** approximately 6,653 lines (excluding the MGraph-DB briefing at 1,732 lines, which is role-dependent).

## Overlap Analysis and Skip Recommendations

Several documents cover overlapping ground. This section identifies where redundancy exists so sessions can avoid loading duplicate material.

### High Overlap: Role-Based Agent Coordination (R1) vs Agentic Workflow Guide (R2)

- **R1** (Role-Based Agent Coordination) defines the architecture: what roles exist, their schemas, issue type definitions, state machines, and submodule structure.
- **R2** (Agentic Workflow Guide) is the practical how-to: how to set up roles, how agents find work, lessons learned, single-repo adaptation.
- **Overlap:** Both describe the six core roles, both show issue type schemas, both explain the Conductor hub pattern.
- **Recommendation:** For a **Conductor or Architect**, load R1 (the authoritative architecture). For a **Dev or QA doing implementation**, load R2 (the practical guide). For a **Librarian**, load both. In a severely token-constrained session, **R2 is the better single choice** because it includes practical advice and lessons learned alongside the core concepts.

### High Overlap: Graph-Based Issue Tracking Briefing (R3) vs Architecture Overview (E3) + Memory-FS (E4)

- **R3** is an executive-level briefing that covers the same architectural ground as E3 and E4 but with more diagrams, use cases, and REST API detail.
- **Overlap:** Repository structure, storage backends, and the graph data model appear in all three.
- **Recommendation:** If E3 and E4 are already loaded, **skip R3 unless the task involves the REST API or explaining the project to outsiders**. R3 adds the REST endpoint reference and use-case scenarios that E3 and E4 lack.

### Moderate Overlap: Thinking in Graphs (E2) vs Lexicon Architecture v2 (R5)

- **E2** establishes the philosophy. **R5** applies it to the Lexicon package design.
- **Overlap:** R5 recaps E2's core principles (anchor nodes, fractal scope, honest uncertainty).
- **Recommendation:** E2 is always essential. **R5 can be skipped unless the task involves the Lexicon, type definitions, or cross-scope analysis.** The recap sections in R5 are brief enough that having both loaded is not wasteful if tokens allow.

### Moderate Overlap: Thinking in Graphs (E2) vs Compatibility Through Connectivity (F14)

- **F14** is an extended exploration of the compatibility concepts introduced in E2 Part 2.
- **Recommendation:** **Skip F14 in most sessions.** E2 covers the same ideas more concisely. F14 is useful only for deep philosophical work on the compatibility model.

### Low Overlap: Type_Safe Guides (F1-F7)

- The seven Type_Safe and formatting guides cover distinct, non-overlapping topics. However, for a Dev session, not all are needed simultaneously.
- **Recommendation:** For a standard Dev task, load **F1** (core Type_Safe) + **F3** (no raw primitives) + **F7** (formatting). Add **F4** (testing) if writing tests. Add **F2** (safe primitives) only if the task involves creating new typed fields. **F5** and **F6** are rarely needed unless working on collection types or decorators.

## Quick Start Subsets

### Minimum Context (~1,390 lines, ~4 documents)

For the most token-constrained sessions where the agent needs only basic orientation:

1. **E1: CLAUDE.md** (~164 lines) -- session bootstrap, repo map, conventions
2. **E2: Thinking in Graphs** (~595 lines) -- core philosophy
3. **E3: Architecture Overview** (~387 lines) -- repo structure and dependencies
4. **E4: Memory-FS Abstraction** (~244 lines) -- storage layer

This set answers: "What is this project? How is it organized? How does storage work?"

### Dev Session (~3,100 lines, ~6 documents)

For a Dev agent implementing features or fixing bugs:

1. **E1: CLAUDE.md** (~164 lines)
2. **E2: Thinking in Graphs** (~595 lines)
3. **E3: Architecture Overview** (~387 lines)
4. **E4: Memory-FS Abstraction** (~244 lines)

6. **F1: Type_Safe Core Guide** (~858 lines) -- coding patterns

Add if writing graph code: **R4: MGraph-DB Briefing** (+1,732 lines).
Add if task involves types/lexicon: **R5: Lexicon Architecture** (+783 lines).

### QA Session (~2,450 lines, ~5 documents)

For a QA agent reviewing code:

1. **E1: CLAUDE.md** (~164 lines)
2. **E2: Thinking in Graphs** (~595 lines)

1. **E1: CLAUDE.md** (~164 lines)
2. **E2: Thinking in Graphs** (~595 lines)

For sessions with ample token budget, load all Essential + Recommended documents:

E1 + E2 + E3 + E4 + R1 + R2 + R3 + R4 + R5

This provides complete project context. Reference tier documents (F1-F17) should still be loaded on demand.

## Document Loading Order

When loading multiple documents, the order matters because later documents build on concepts from earlier ones.

**Recommended loading order:**

1. **E1: CLAUDE.md** -- bootstraps the session, lists all repos and conventions
2. **E2: Thinking in Graphs** -- establishes the mental model before architecture
3. **E3: Architecture Overview** -- maps the repos that E2's concepts inhabit
4. **E4: Memory-FS Abstraction** -- explains the storage underpinning
5. **R1: Role-Based Agent Coordination** -- how the team is structured (depends on E3)
6. **R2: Agentic Workflow Guide** -- how to operate within the team (depends on R1)
7. **R3: Graph-Based Issue Tracking Briefing** -- REST API and use cases (depends on E3, E4)
8. **R5: Lexicon Architecture v2** -- vocabulary layer (depends on E2, E3)
9. **R4: MGraph-DB Briefing** -- graph database internals (depends on E2)

## Notes for Maintaining This Guide

- **Update when documents are created, renamed, or superseded.** The paths and line counts in this guide become stale if the docs repo is reorganized.
- **Review tier assignments when roles expand.** The addition of Cartographer, AppSec, Historian, and Journalist roles (post-original six) means their role-specific docs may need to move from Reference to Recommended as those roles mature.
- **Track the Lexicon implementation.** Lexicon Architecture v2 (R5) describes a planned package. Once `Issues-FS__Lexicon` exists as a real repo with code, additional implementation docs will need to be catalogued.
- **Monitor Type_Safe version drift.** The Type_Safe guides reference specific osbot-utils versions (v3.28.0, v3.63.3, v3.63.4). When osbot-utils upgrades, check if the guides need updating or if newer versions exist.
- **The `to_classify/` directory is temporary.** Many documents there are awaiting proper placement. As the Librarian or a docs reorganization effort moves them, update this guide's paths accordingly.
- **CLAUDE.md is always auto-loaded.** It is injected as project instructions by the Claude Code session infrastructure. This guide assumes it is always present. If the session infrastructure changes, E1 may need to be loaded manually.
