## 2. Cross-References to February 10 Briefs

### Brief #32 (Simplified Agent Format) -- Cross-References

This brief has dense connections to the Feb 10 batch. It represents the convergence of several threads that were identified separately but had not yet been synthesised into a single proposal.

#### Direct Ancestor: #5 Evolving Complexity and Frictionless Capture (v0.1.2)

This is the strongest connection. Brief #5 stated the core principle: "Issues FS must support growing complexity and growing richness without requiring it upfront." It identified the forced folder structure as a friction problem and proposed configurable readers as the solution.

Brief #32 delivers on that promise concretely. The `.issues` flat file format is the "just a text file" end of the complexity spectrum. The key insight from #5 -- "The structure on disk is just a serialisation choice. As long as we have a reader for that format, we support it." -- is exactly what #32 implements. The `.issues` format IS a new reader/serialisation format.

However, #32 goes beyond what #5 described. Where #5 proposed accepting any input format (CSV, YAML, markdown lists), #32 proposes a specific **canonical** simplified format with its own file extension, its own inference rules, and its own validation command. This is not just "another reader" -- it is a first-class alternative representation designed to become the primary creation format for agents.

**Librarian note:** The configurable reader architecture from #5 should be the implementation vehicle for #32. The `.issues` parser should be a reader class, not a separate code path.

#### Direct Ancestor: #7 File Structure & Path Architecture Refactoring (v0.1.2)

Brief #7 established the three-layer separation: Content Layer / Path Layer / Storage Layer. Brief #32 respects this by design -- the `.issues` format is purely Content Layer. It contains labels, statuses, descriptions, and hierarchy. It never specifies paths, folder names, or storage locations. The Path Layer and Storage Layer handle the mapping from `.issues` content to the full in-memory graph and then to whatever on-disk structure is needed.

The normalisation command (`issues-fs normalise`) from #32 is effectively a round-trip through the layers: parse the `.issues` format (Content Layer) into the graph (in-memory), then write out via the standard Path Layer conventions (JSON files in folder structure).

**Librarian note:** This confirms that #7's architecture holds. The `.issues` format validates the layer separation rather than challenging it.

#### Direct Ancestor: #6 File System as Transaction Store (v0.1.2)

Brief #6 established the LETS principle: every action saves state. Brief #32 makes this dramatically easier. If creating 10 issues means writing 10 lines in a text file (instead of creating 30 files across 15 directories), the barrier to saving state drops by an order of magnitude. The `.issues` format is the LETS principle's best friend -- it makes frequent, granular state capture almost frictionless.

The `issues-fs check` command from #32 also connects to #6's emphasis on being able to "understand what happened" and "recover." The check command verifies the graph's consistency, which is a form of state verification after transformation.

#### Sibling: #29 Mass Issue Creation, Transactions, and Deltas (v0.1.5)

Brief #29 asked: "What's the right way to mass-create and mass-edit issues?" and evaluated five approaches (raw JSON, REST API, Python code, batch JSON, CLI batch mode). It concluded that Python code was the best interface because it supports assertions and transaction safety.

Brief #32 introduces a sixth approach that was not considered in #29: the `.issues` flat file. This approach competes with and arguably supersedes the "batch JSON" option from #29, and it may displace Python code as the primary mass-creation method for the 80% case. Python code remains superior when transaction safety, preconditions, and complex logic are needed. But for the simple case of "create 10 tasks," the `.issues` format is unambiguously better.

**Librarian note:** The transaction model from #29 (snapshot, verify, apply, verify, commit/rollback) still applies. The `issues-fs check` command from #32 is the "verify" step. The two briefs are complementary, not contradictory.

#### Sibling: #16 CLI-First GitHub Integration and Use-Case Repos (v0.1.3)

Brief #16 established the CLI as the primary interface for both humans and agents. Brief #32 extends this with two new CLI commands: `issues-fs check` (or `verify`) and `issues-fs normalise`. These fit naturally into the CLI command structure from #16.

Brief #16 also established the use-case repo pattern: standalone, focused, immediately useful tools built on Issues FS. The `.issues` format could become the backbone of several use-case repos -- any tool that needs to represent a set of tasks or findings could use it as the default output format.

The agent workflow described in #32 (create/edit `.issues` file, run `issues-fs check`, fix errors, commit) maps directly to the CLI-as-API pattern from #16, confirming that design direction.

#### Sibling: #31 Spreadsheet View, Graph Editor, and Batch Workflows (v0.1.5)

Brief #31 proposed a text box mode where "each line is a new issue" and batch creation via typing: "Implement login validation" then Enter, "Add password reset flow" then Enter, and so on. Brief #32's `.issues` format IS this text box mode, but as a file rather than a UI widget. The two briefs converge on the same insight: the fastest way to create issues is one line per issue.

The key difference is that #31 envisioned this in a UI context (with a schema-aware dropdown for issue type), while #32 envisions it as a file format (with type inference from prefixes and context). Both are needed. The UI text box mode could generate `.issues` files, or the `.issues` format could be the backing store for the text box mode.

#### Related: #14 Transformations, Round-Trips, and Ideas Library (v0.1.2)

Brief #14 established the universal input principle: accept any format and transform it into Issues FS. The `.issues` format is a new entry in the transformation family. More importantly, #32's normalisation command is a round-trip: `.issues` -> graph -> JSON. The fidelity of this round-trip is testable using #14's round-trip verification principle.

Brief #14 also proposed "suggested graphs" -- when a user starts mapping something, propose the graph they might want. The `.issues` format could be the output format for suggested graphs: "Here are the issues we think you want, in a format you can review and edit in 10 seconds."

### Brief #33 (The Briefing Workflow) -- Cross-References

#### Direct Ancestor: #15 Voice Memo Processing, Content Principles, Post-Commit Actions (v0.1.2)

Brief #15 described the voice memo processing workflow and asked the Librarian to design the debrief document format. Brief #33 delivers that design -- but at a much larger scale than #15 envisioned.

Where #15 described processing a single voice memo into tasks, notes, actions, ideas, and questions, #33 describes the full cycle: voice memo -> transcription -> Claude refinement -> polished brief -> parallel agent execution -> individual role responses -> consolidated debrief -> human review -> next cycle.

The debrief format from #33 is more specific than what #15 requested. It is a consolidated document with summaries and links to individual role responses, placed in a `debriefs/` folder that mirrors the `briefs/` folder.

**Librarian note:** The voice memo processing workflow from #15 should be considered **superseded in scope** by #33. Brief #33 subsumes #15's workflow and adds the execution and consolidation phases. However, #15's content principles (issues are not master sources of data; file-link issue type) remain independently valid and are not addressed by #33.

#### Direct Ancestor: #3 Daily Workflow, Role Status, and Dashboard (v0.1.2)

Brief #3 asked: "What's the status of what's going on?" and proposed a daily query to every role for a status report. Brief #33 answers this at a higher level of abstraction. The brief/debrief cycle IS the status mechanism -- each debrief is a consolidated status report produced as a natural side effect of the work itself, not as a separate reporting burden.

Brief #3 established the Librarian as the first point of contact. Brief #33 partially shifts this -- the master agent (Claude Code Web) handles orchestration and consolidation, while the Librarian may contribute to the debrief by ensuring cross-references and knowledge integration.

#### Related: #4 Dev Workflow: Atomic Branches and Review (v0.1.2)

Brief #4 mandated context-complete task briefs and detailed change explanations. Brief #33's workflow makes this natural: the brief IS the context-complete task description, and each role's response IS the change explanation. The brief/debrief cycle is a higher-level instantiation of the atomic-branch review pattern.

#### Related: #8 Issues FS Status, Personas, and Dev Discipline (v0.1.2)

Brief #8 requested brief-to-task traceability: "every task linked back to originating brief." Brief #33's folder structure (briefs in one folder, debriefs in a parallel folder, role responses in role-specific folders) makes this traceability structural rather than manual. Each debrief links to the brief it responds to, and each role response links to both.

## 4. The Briefing Workflow Brief (v0.2.33) and the Debriefs Folder

### What v0.2.33 Describes

Brief #33 formalises a symmetrical communication pattern:

- **Briefs** flow top-down: human -> team (stored in `humans/<name>/briefs/MM/DD/`)
- **Debriefs** flow bottom-up: team -> human (stored in `humans/<name>/debriefs/MM/DD/`)
- **Role responses** are written to each role's own area (stored in `roles/<role>/reviews/YY-MM-DD/` or similar)

The debrief is a consolidation document that links to all individual role responses, providing the human with a single entry point for review.

### How This Affects Debriefs Folder Organisation

Currently, the `humans/Issues-FS__Dev__Human__Dinis_Cruz/` repo has a `briefs/` folder organised by `MM/DD/`. The repo does NOT yet have a `debriefs/` folder. Brief #33 calls for creating one with a mirroring structure.

The key organisational decisions are:

1. **Temporal mirroring**: The debriefs folder should use the same `MM/DD/` structure as briefs. A debrief for briefs delivered on `02/13/` goes in `debriefs/02/13/`. This makes the correspondence between input and output immediately navigable.

2. **Naming convention**: Debriefs should reference the brief(s) they respond to. Proposed convention:
   ```
   v{version}__debrief__{brief-identifier}.md
   ```
   Example: `v0.2.16__debrief__simplified-agent-format-responses.md`

3. **One debrief per brief batch, not per brief**: If the human delivers three briefs in one session, and the team processes them in one orchestration pass, the debrief should be a single document covering all three. This prevents fragmentation and mirrors the human's experience of sending a batch and wanting a consolidated response.

4. **The debrief links OUT, not IN**: The debrief document itself should be lean -- summaries and links. The substantive content lives in each role's response. This follows the content principle from brief #15: the debrief is not the master source of data; the role responses are.

### Librarian's Role in the Debrief Cycle

Brief #33 positions the master agent (Claude Code Web) as the debrief creator. However, the Librarian has a natural role in this process:

- **Quality check**: Verify that the debrief links to all role responses, that no role's output was missed, and that the summary accurately represents the individual responses.
- **Cross-reference enrichment**: Add links from the debrief to related briefs, decisions, and existing documentation. The master agent may not have the Librarian's graph awareness.
- **Archive maintenance**: Ensure the debrief is properly catalogued and that the brief/debrief pair is linked in the knowledge graph.

## 5. Folder Structure Recommendations for the Brief/Debrief Pattern

### Recommended Structure for the Human's Repo

```
humans/Issues-FS__Dev__Human__Dinis_Cruz/
  briefs/                               # Human's input (top-down)
    02/
      09/
        v0.1.0__brief_next-steps.md
      10/
        v0.1.1__decision__workstream-and-iteration-naming.md
        v0.1.2__briefs__daily-workflow-role-status-and-dashboard.md
        ... (29 more briefs)
      13/
        v0.2.16__briefs__issues-fs-simplified-agent-format.md
        v0.2.33__briefs__the-briefing-workflow-voice-memo-to-agentic-execution.md
  debriefs/                             # Team's consolidated output (bottom-up)
    02/
      13/
        v0.2.16__debrief__feb-13-briefs-consolidated.md
```

### Recommended Structure for Role Responses

```
roles/Issues-FS__Dev__Role__<Role>/
  docs/
    responses/                          # Role's individual responses to briefs
      v0.2.16__response__<topic>.md     # Response to a specific brief
      v0.2.33__response__<topic>.md
    reviews/                            # Role's reviews (broader than brief responses)
      ...
```

I am using `docs/responses/` rather than `reviews/YY-MM-DD/` as proposed in brief #33, for the following reasons:

1. **Consistency with existing structure**: The Librarian repo already uses `docs/` as the top-level folder for all documents. Adding `responses/` as a subfolder is consistent.
2. **Version-in-filename over date-in-folder**: The version prefix in the filename (`v0.2.16__`) already provides temporal ordering. A separate date folder adds nesting without adding information. The `MM/DD/` structure makes sense for the human's briefs (where there may be many per day and the human thinks in dates), but roles produce fewer, more targeted responses where the version reference is more useful than the date.
3. **Discoverability**: A flat list of responses in one folder is easier to scan than nested date folders, especially when the volume per role is moderate.

However, if the team standardises on the `reviews/YY-MM-DD/` pattern as described in #33, the Librarian will adopt that structure. The recommendation above is the Librarian's proposal; the Conductor or Architect should make the final call.

### Recommended Naming Conventions

**Briefs** (from human):
```
v{project-version}__briefs__{descriptive-slug}.md
v{project-version}__decision__{descriptive-slug}.md
v{project-version}__daily-brief__{sequence}__{descriptive-slug}.md
```

**Role Responses** (from roles):
```
v{brief-version}__response__{descriptive-slug}.md
```

**Debriefs** (consolidated, from master agent or Librarian):
```
v{project-version}__debrief__{descriptive-slug}.md
```

The version prefix on a response matches the brief it responds to, creating an explicit traceability link. The version prefix on a debrief matches the project version at the time of consolidation.

**Option A: Extend the existing catalogue.** Add rows 32-33 to the master table. Add the new Cluster 9. Update the cross-references section. Advantages: single catalogue for all briefs. Disadvantage: the document is already 460+ lines long and may become unwieldy.

**Librarian recommendation: Option B.** As the brief count grows, a single catalogue will become impractical. Batch catalogues with a master index scale better and are easier to maintain. Each batch catalogue can provide deep analysis of its own briefs while the master index provides the bird's-eye view.
